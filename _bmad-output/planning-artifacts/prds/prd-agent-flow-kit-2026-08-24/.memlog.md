- (decision) PRD covers portability, safe lifecycle maintenance, drift detection, runtime readiness, and cross-host verification for agent-flow-kit; broader AI Agent Control Plane redesign is excluded.
- (decision) Git is the durable authority for shared kit content; reconciliation must preserve explicitly machine-local state and refuse destructive guesses when managed state has unexplained changes.
- (decision) Claude Code and Codex are first-class native-subscription runtimes; no personal credential centralization or silent metered fallback is permitted.
- (decision) Orca owns coding-session mechanics and visibility; central agent-router owns resource recommendation and late-bound local placement; agent-flow-kit owns opt-in autonomous delegation/control flow.
- (decision) PR #5 is experimental engineering evidence only and will be evaluated after requirements mature; it is not requirements authority or accepted implementation.
- (decision) Success requires real-host adoption, update, preservation, idempotence, managed-drift detection, runtime integration checks, restoration, and second-host portability proof; fixture-only validation is insufficient.
- (decision) Stakes calibrated as internal fleet infrastructure with meaningful operational risk; favor explicit ownership, fail-safe behavior, recoverability, and diagnosability over clever automation.
- (decision) Use Coaching path with Vision + Features entry point so product decisions are made explicitly rather than inferred from current implementation or PR #5.
- (event) Architecture source pack will be reconciled incrementally before finalization, covering invariants, ownership boundaries, MVP scope/done criteria, unresolved gaps, and visibility/UX.
- (decision) End-state promise: a supported Orca host can explain whether agent-flow-kit is managed, current/stale, intentionally adapted, or unexpectedly drifted; safely converge or stop with actionable human guidance; and make a trustworthy orchestration-readiness assertion.
- (decision) Every supported host must prove lifecycle correctness and meaningful execution readiness, including safe repeatable update, local-state preservation, managed-drift detection, native runtime/integration usability, credential/spend boundaries, and eligibility for orchestration.
- (decision) Increment acceptance requires at least one full real-host path from approved BMAD work through explicit Orca orchestration, central routing, agent-flow-kit dispatch, fresh Orca-visible worker, expected runtime/persona, and deterministic gates.
- (decision) Additional representative hosts require full lifecycle proof plus a harmless routed worker-launch smoke path; repeat the full path only when host-specific differences warrant it.
- (decision) A ready verdict must support operator trust: approved orchestration may proceed without manually re-auditing the installation.
- (decision) Freeze four product capabilities: installed state/ownership/drift; safe lifecycle/convergence; compatibility/dependency/execution readiness; lifecycle/operator visibility. Real-host portability/execution proof is the cross-capability acceptance track.
- (decision) Each host locally inventories canonical revision, applied/adopted revision, components, ownership, integrity/version metadata where appropriate, BMAD targets, and state; the manifest contains no secrets and has no routing authority.
- (decision) Lifecycle provides one obvious entry point with status, adopt/sync, update, and verify semantics; preserves declared local state, blocks unexplained drift, emits NEEDS_OWNER when deterministic convergence is impossible, protects recoverability for risky global edits, and never reports partial failure as success.
- (decision) Readiness validates but does not install Claude, Codex, Orca, BMAD wiring, router, or validator/client; native auth/subscriptions remain harness-owned, credentials never enter kit state, and silent metered fallback is forbidden.
- (decision) Lifecycle visibility must be human-readable and scriptable across revision, applied revision, component, ownership, state, drift/update, readiness, and action required; no new general observability subsystem.
- (decision) Explicit exclusions include centralized fleet services, background reconciliation, dashboards, control-plane/router/Kubernetes/GPU/local-agent/model/secrets work, automatic harness installation/upgrades, additional harnesses, and unrelated orchestration enhancements.
- (decision) Known adaptation is deterministic only: schema-declared local ownership or an explicit secret-free registered exception; heuristic or LLM inference is forbidden, and all unexplained kit-owned differences are LOCAL_DRIFT.
- (decision) Legacy adoption is inspect-only first: auto-adopt only mechanically proven equivalent state; owner-approved deterministic plan for ambiguous or mutating conversion; refuse with NEEDS_OWNER when ownership, preservation, security, policy, compatibility, or product boundaries cannot be protected.
- (decision) Readiness states are READY, READY_WITH_ADAPTATION, READY_WITH_WARNINGS, NOT_READY, and NEEDS_OWNER, aggregated by strongest condition while retaining per-component results and criticality.
- (decision) Compatible stale or noncritical conditions may warn without blocking; broken required components and mandatory dependency failures are NOT_READY; execution-critical drift or ownership ambiguity is NEEDS_OWNER; noncritical drift still blocks overwrite.
- (decision) Lifecycle dependency status must not invent fallback routing: missing optional harness may disable only that harness if another centrally approved route remains executable.
- (decision) Adopt/update/verify do not activate orchestration; planning and orchestration remain separate, with explicit human invocation after approved scope.
- (change) Historical route-to-stamp-to-validator-to-Orca proof gap is closed by EPIC-035 Phase B and must not be carried forward as current status.
- (decision) Every mutation computes a full plan; safe conflict-free adopted-host convergence may run unattended, while ambiguous ownership or reinterpretation requires explicit approval.
- (decision) Status and verify are strictly read-only; verify proves rather than repairs. Adopt establishes ownership only after inspect/reconcile/verify, and update mutates only eligible adopted state.
- (decision) Mutation requires deterministic repository identity, exact commit, clean canonical inputs, and explicit lifecycle/schema compatibility; detached, non-default, older, or noncanonical revisions require explicit source-selection or rollback intent.
- (decision) Git revision selection remains external: lifecycle does not fetch/pull/merge/rebase/switch branches in this increment.
- (decision) Update source eligibility and installed execution readiness are separate dimensions; a dirty test checkout can block update without invalidating a verified installed revision.
- (decision) Managed sections preserve outside content; recognized canonical content may update, registered adaptations follow declared rules, unexplained inside edits stop with LOCAL_DRIFT/NEEDS_OWNER, and LLM conflict merging is forbidden.
- (decision) Mutation preflights the complete set, captures secret-free recovery evidence, defaults to deterministic rollback, detects interrupted operations before new mutation, and never treats partial state as success.
- (decision) Applied revision commits last and only after complete mutation plus deterministic verification; repeated update at current state is a stable no-op.
- (decision) Readiness is scoped as HOST_EXECUTION_READY, NEW_WORK_READY, TARGET_READY(repo), and ROUTE_READY(stamp); failures block the narrowest invalidated scope.
- (decision) Host execution requires verified kit, usable Orca, compatible validator/client, and at least one centrally approved usable harness path; fresh routing additionally requires router reachability.
- (decision) Claude and Codex are individually optional first-class harnesses; an accepted route selecting an unavailable harness must not launch or substitute locally, and instead requires reroute, compatible host, or owner action.
- (decision) Execution-critical readiness proves safe capabilities beyond presence; routine verify stays non-destructive, while actual visible worker creation is an acceptance test unless a safe dry-run exists.
- (decision) Validator readiness requires compatible identity/contracts plus positive and negative fixtures so an always-success implementation cannot pass; live route/stamp smoke is explicit and harmless.
- (decision) Native harness readiness must safely prove auth/session and invocation semantics without exposing credentials; unauthorized metered/API-key redirection blocks the affected route with no automatic spillover.
- (decision) Compatibility is the intersection of router-approved profile, kit-supported launch contract, host capabilities, target BMAD contract, and valid stamp; each subsystem retains authority over its own machine-readable contract.
- (decision) Unknown safety/correctness-critical compatibility blocks the affected route; bounded noncritical uncertainty may warn when required capabilities are positively proven.
- (decision) Existing agent-stamp-validate bridge may remain transitional, but prox-ops source checkout is not the long-term validator/client distribution contract.
- (decision) Human and machine lifecycle output derive from one normalized result model; machine output has a documented versioned schema with stable states, reasons, blocking scopes, and coarse exit semantics.
- (decision) Machine results distinguish false/absent/not-evaluated/unavailable and expose component, ownership, state, reason, severity, blocked scope, owner action, transience, mutation safety, and operation success without prose parsing.
- (decision) Warnings/failures include bounded expected/observed evidence, provenance, impact, owner, safe next action, and recovery guidance; hashes/identifiers are preferred over arbitrary content dumps.
- (decision) Lifecycle output never emits tokens, credential values/content, authorization headers, or credential-store contents; it may report safe auth state, source category, and redacted conflicting variable names.
- (decision) Status/verify default offline; explicit live mode uses bounded non-mutating probes and distinguishes transient unavailability from deterministic failure without persisting availability as installed truth.
