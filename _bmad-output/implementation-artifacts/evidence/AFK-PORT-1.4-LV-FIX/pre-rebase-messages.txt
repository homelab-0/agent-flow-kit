=== bbc84b1a22af1b20e83a5c24233c0e35227fbfea
Close the xtrace credential channel and the stale-result window in the gateway launch

The gateway-backed local launch assigns the resolved credential to a shell
variable before env -i, so an xtrace inherited from the terminal's own shell
(a set -x in a login rc, or a BASH_ENV) renders the value into the terminal
buffer Orca persists. The generated text now opens with `set +x;`, which closes
that channel. The native launch text assigns nothing and is byte-identical to
what it was; the suite asserts both halves.

rm -f on the result file moves above the gateway preflights. It sat after them,
so a refusal left the previous cycle's claude-result.json on disk for anyone who
opens the file by name.

Two test gaps: the terminal-read stub now takes a status knob, so the suite can
drive a terminal to its end state and assert that a launch ending without a
CLAUDE_EXIT line is reported as a launch failure with no result artifact — the
class's most important safety property, previously argued rather than tested.
A second case pre-creates a stale result artifact and checks a refusal clears it.

Two documentation sentences claimed more validation than happened: the contract
doc now separates the four live-validated variables from the context-window
variable the catalog records as observed, and the dispatch.sh header says the
launch classes' contracts are live-validated rather than the implementations.

The record's account of the credential's exposure window was wrong.
/proc/<pid>/cmdline is world-readable absent hidepid, so the pre-exec window is
not same-user-only; the corrected text names hidepid=2 as the interim
mitigation and keeps the wrapper-shell fix as a contract question.

=== 533880df5369d6d58b663ccbe61a345a26bf40d9
Add a gateway-backed launch class for local profiles on the claude harness

The launch adapter had one validated way to start claude: a native vendor
subscription session. A profile the catalog marks hosting: local is reachable
only through the gateway, so the adapter refused it — routable and unlaunchable
at the same time.

This adds the second class. It is the native launch plus five per-process
variables inside the same env -i allowlist: the gateway endpoint, the scoped
key, the model pin, the x-placement header copied verbatim from the /v1/place
result fetched for that attempt, and the profile's real context window. The
claude invocation itself is byte-identical to the native one, which the tests
now check by comparing the two builders directly rather than by eye.

The credential is resolved by the terminal at launch time from a 1Password
reference the launcher configures; only the reference and the service-account
env file are ever in the command text, and an empty read stops the launch
before claude starts rather than letting an unauthenticated session run.

Admission is narrow and reads the stamp plus the trusted catalog: claude, the
catalog marking the profile local, placement required, no entitlement pool,
cost class free. Everything else keeps refusing, and a local profile stamped
with a vendor pool is refused by name. Readiness mirrors the two classes, and
the lifecycle contract document describes both.
